The engine is Rust compiled to WebAssembly, so the question every page has to answer is what it
buys and what it costs. This page gives the figures for the engine **on its own**: no browser,
no rendering, no network — the module that answers a query, loaded in Node. They are measured,
dated, and repeatable with one script.

## What was measured

Measured on 14 November 2026 on an **Apple M4 Pro** (arm64), Node 24, with
`scripts/measure-queries.mjs`: one run thrown away, then nine, **median** shown with the
fastest and the slowest in brackets. Other programs were running on the machine, so a quiet one
will be a little faster. The rows are ten columns of the conformance data set's
shape — integers, text, an exact decimal, a float, a boolean, a date and a timestamp — as CSV.
The two load times are of 16 November 2026, after the CSV reader's third pass: about 170 MB of
CSV a second; the three grouping rows are of the same day, after grouping by a text
dictionary's codes.

| 100,000 rows (CSV 7.4 MB) | Median | Range |
|---|---|---|
| Load the CSV | 59 ms | — |
| Filter: country and amount, first 100 rows | 1.6 ms | 1.6–3.8 ms |
| Text search in a column, first 100 rows | 2.2 ms | 2.1–2.3 ms |
| Sort by amount, top 100 | 3.0 ms | 2.9–3.4 ms |
| Group by country, sum and count | 5.0 ms | 4.9–6.8 ms |
| Group by customer (500 groups), sum | 4.0 ms | 3.9–4.2 ms |
| Pivot: country and customer, sum and count | 20 ms | 20–21 ms |
| **Module memory** after the load | **13.2 MiB** | |
| of which the columns | 4.1 MiB | |

| 1,000,000 rows (CSV 74.6 MB) | Median | Range |
|---|---|---|
| Load the CSV | 0.44 s | — |
| Filter: country and amount, first 100 rows | 14 ms | 14–15 ms |
| Text search in a column, first 100 rows | 21 ms | 21 ms |
| Sort by amount, top 100 | 26 ms | 25–26 ms |
| Group by country, sum and count | 55 ms | 54–57 ms |
| Group by customer (500 groups), sum | 41 ms | 41–42 ms |
| Pivot: country and customer, sum and count | 190 ms | 189–201 ms |
| **Module memory** after the load | **121 MiB** | |
| of which the columns | 41 MiB | |

Ten times the rows cost about ten times the time and about nine times the memory: the engine
scans typed columns, and nothing in these queries grows faster than the data.

## Two numbers for the engine's memory

The **columns** — the data itself, typed — take 4.1 MiB for 100,000 rows and 41 MiB for a
million: about forty-three bytes a row for these ten columns and the three derived from them. An
integer takes as many bytes as its largest value needs — one for a count of 0–39, four for an id up
to a million, eight at most — and stays an integer. A text column with few distinct texts (a
country, a status, a customer of a few hundred) keeps each text once and a code of one or two bytes
a row; a column of distinct texts stays as it was. A filter or a search on such a column tests each
distinct text once, not each row, which is why the search above takes half the time. An exact
decimal stays exact, and takes eight bytes up to 18 digits of precision, which an amount is
(`decimal(12, 2)`), and sixteen above, a timestamp keeps its microseconds, and a missing value costs a bit in a
bitmap rather than a boxed object. The price is on the way in: loading takes about a tenth longer,
for the lookup of every text.

The **module memory** is larger, 13.2 and 121 MiB, because it also holds the room that reading
the CSV needed — the file's copy in the module, 71 MiB for the million rows — and WebAssembly
memory only grows. That is the number a page pays, and the one the engine's budget guards:
`peakmark.toml` fails a release whose scenario (100,000 rows loaded, queried and pivoted) needs
more than 26 MiB, or leaks from one run to the next. The queries add nothing to it: ten rounds of
all of them leave it where the load put it.

A file loaded **piece by piece** (`loadStream`, 4 MiB at a time) does not need the copy: the same
million rows leave the module at 62 MiB after the load and after the queries, which take their
temporaries from the same room.

The numbers are the same in the tab and on a server, because it is the same code.

A sort by a **locale** (`"collation": "de"`) asks the collator for a sort key of each distinct text, not of each row, when the column has few of them. A million rows by `customer` (500 texts) take 17 ms for the first 100 rows and 114 ms for rows 500,000 on, against 15 and 77 ms for the binary order (16 November 2026, same machine; before, 501 and 609 ms).

## What the whole page holds

The engine's own memory is not what the browser shows. Measured in Chromium, the engine in a
Worker: the resident memory of the browser's whole process tree, minus an empty page's, after
a CSV file of the same shape (six columns) has been fetched and loaded. The page keeps no rows of
its own: a page that holds a million JavaScript objects pays for them on top.

| Rows | File | `load` of the bytes | `loadStream` of the response |
|---|---|---|---|
| 100,000 | 4.1 MB | 50–53 MiB | 45–46 MiB |
| 1,000,000 | 43 MB | 172–175 MiB | 142–145 MiB |

So the engine is **compact, not free**: it keeps its own typed copy of the data — about 160 MiB
for a million rows, 140 when the file is read in pieces (these two figures and the table are from
before the integers and the texts were stored compactly, which took 71 MiB off the module of a
million rows) — next to whatever the page holds.

A page that has its rows as JavaScript objects hands them over with `loadRows`, which turns them
into typed columns in pieces of 65,536 rows and does not make a JSON text of the table. Measured
the same way, on a page that generates its million objects itself (so the objects are in the
figure): 386 MiB, 1,000,000 rows, and the first rows on screen after 0.27 s. Before, as one JSON
text, it was 847 MiB and 1.2 s; for 100,000 rows 128 MiB and 0.1 s against 158 MiB and 0.17 s.

**Using the grid adds to that once, not each time.** After the first scroll through the table the
same process tree holds about 55 MiB more, for 100,000 rows and for a million alike: it is what
Chromium keeps for painting, in its renderer and GPU processes. The engine's memory, the page's
JavaScript heap and the number of elements in the grid stay where the load left them. Sorting and
filtering add nothing measurable, and ten more rounds of sort, filter and scroll add about 15 MiB
before it levels off.

## Loading again

WebAssembly memory grows and is never handed back to the browser. Inside the module, the
allocator reuses what a table frees, so a page that loads again stays at its **high-water mark**
instead of growing with each load. That high-water mark is set by how a page loads.

Measured on 16 November 2026 in Chromium on the same M4 Pro with `scripts/measure-reload.mjs`.
The engine runs in a worker, and each load is a million rows of the shape above. The table shows
the engine's memory (`stats().memory`) and the physical footprint of the browser's whole process
tree, minus the page with its CSV already fetched. Each row is a single run.

| Ten loads of 1,000,000 rows | Engine, after load 1 → 10 | Browser, after load 10 |
|---|---|---|
| Same name, `load` of the bytes | 173 → 251 MiB, flat from load 2 | 320 MiB |
| Same name, `loadStream` | 112 → 214 MiB, flat from load 3 | 210–295 MiB |
| Ten names, `loadStream` | 112 → 844 MiB, +82 MiB a table | 826 MiB |
| Same name, `unload` before each `loadStream` | 112 MiB, flat from load 1 | 126–221 MiB |
| Same name ten times, then `terminate()` | — | 5 MiB |

- **A name loaded again replaces its table, all or nothing.** The new table is built in full
  before the old one goes, so a load that fails keeps the old data. For that moment both tables
  are in memory, and the high-water mark is about two tables. Fragmentation adds nothing
  measurable: two tables of 112 MiB leave 214 MiB.
- **Another name keeps the old table.** A page that switches between data sets under new names
  adds them up, until it lets one go with `unload(name)`.
- **`unload` before a load keeps the mark at one table.** The table goes first, and the load takes
  its room. The price is that there is no data while the load runs, and none if it fails. A grid on
  the name answers a query in between with an unknown source.
- **`terminate()` hands everything back.** It stops the worker, and its memory goes with it. A
  new provider that loads and answers once took 0.54 s, against 0.51 s for the same load into a
  worker already running. A page that is done with a data set can start over that cheaply.

So a page that loads data again and again uses one name and `loadStream`. It calls `unload` first
when one table's room matters more than keeping the old data until the new data is there. It ends
the worker when it is done with all of it. The server mode keeps only the window in the browser.

## What a page pays

The engine is a module the page loads before its first query. Compressed with Brotli:

| Module | Size | Loaded |
|---|---|---|
| The engine (`engine/`) | about 172 KiB | when the page starts the engine |
| All three elements (`pkg/`) | about 348 KiB | with the elements |
| The collation of a locale (`collation/`) | about 325 KiB | only by a sort that names a locale |
| The XLSX writer (`xlsx/`) | about 240 KiB | only by an export to a workbook |

Sizes are kept inside budgets in `peakmark.toml`, so a release that grows one fails the build
until the growth is explained. A table of fifty rows does not need an engine, and the page
that only reads it should not pay for one.

## In a worker

The engine runs in a Web Worker as it runs on the page, so a query does not block the main
thread. The [live demo](https://og-vanilla.casoon.dev/large-data) queries 100,000 rows that way.
The figures above are the engine's own time; what the page adds is the transfer of the answer and
the drawing of the rows on screen.

## In server mode

With a [REST provider](../where-queries-run/) the rows stay in the database. The grid asks for
the window it shows — 40 rows by default — and the database filters, sorts, groups and counts.
What a reader waits for is then the server and the database, not the engine in the tab.

Measured on 16 November 2026 on the same **Apple M4 Pro**: `opengrid-server`, release build,
with one source, answering `POST /query` over the loopback in the binary result form, as
`createRestProvider` asks. PostgreSQL 16 ran on the same machine; SQLite is compiled into the
server. The rows are those of the engine figures above, generated by the database. Indexes as a
page tuned for these requests would have them: the key `id`, and `(country, amount)` for the
filtered window. One run thrown away, then nine, **median** shown; other programs were running
on the machine.

| A window of 40 rows, or a grouping | PostgreSQL, 1M | PostgreSQL, 10M | SQLite, 1M | SQLite, 10M |
|---|---|---|---|---|
| First window, sorted by `id` | 13 ms | 181 ms | 1.7 ms | 18 ms |
| Window in the middle (`offset` half the rows) | 32 ms | 396 ms | 12 ms | 119 ms |
| Filter on country and amount, sorted by amount | 48 ms | 513 ms | 1.8 ms | 16 ms |
| Text search in a column, any case | 80 ms | 957 ms | 121 ms | 1.18 s |
| Group by country, sum and count | 65 ms | 905 ms | 104 ms | 1.03 s |
| Count of every row (`limit` 0) | 13 ms | 168 ms | 1.6 ms | 18 ms |
| **Server's peak memory** | 9.5 MiB | 9.4 MiB | 16 MiB | 17 MiB |

A window's answer is 3.3 KiB on the wire, a grouping's 352 bytes, whatever the table's size. The
server's memory is the whole process — server and the measuring client — and stays the same for
ten times the rows; PostgreSQL's own memory is not in it, SQLite's page cache is.

What the figures say:

- **Every window carries its count, and the server remembers it.** `total_count` is what the grid
  needs for its scroll bar and `aria-rowcount`, and it is a second statement. In PostgreSQL
  counting ten million rows takes about 170 ms, and that is most of the first window's 181 ms. The
  server therefore keeps the count of a query for 5 seconds (the filter, grouping and aggregates
  are the key; the sort and the page are not) and tells the connector, which skips the statement.
  `notify_changed` drops it at once; `count_cache_ttl` sets the time, zero switches it off. The
  figures above are measured with it off; with it on, a window after the first one of a query
  (PostgreSQL, 10M, 17 November 2026, same machine, median of nine): the first window 146 ms
  became 0.5 ms, the filtered window 461 ms became 246 ms, the grouping 631 ms became 370 ms,
  the text search 743 ms became 1.4 ms. A count is stale for at most that time when the
  database changes without the server being told.
- **A window far down costs more.** An `offset` makes the database walk past the rows before it:
  dragging the scroll bar to the middle of ten million rows asks for 400 ms in PostgreSQL (227 ms
  with the count remembered, so the walk is what is left). Keyset paging would avoid the walk
  from a window on, not for a jump to a position, which is what the scroll bar does; it is not
  built. An index on the sort column is what shortens it.
- **The indexes decide, not opengrid.** With an index on `amount` alone, SQLite takes it for a
  range over half the table: the filtered window then needs **5.5 s** at ten million rows instead
  of 16 ms. A text search with `contains` reads every row in either database.
- **Compared with the tab.** A million rows in the engine answer a filter in 15 ms and a grouping
  in 55 ms, once the page has loaded them (0.44 s, 121 MiB in the engine). The server answers in
  the same order of magnitude, puts nothing but the window into the browser, and answers from the
  current data each time.

Not measured here: the network between browser and server, which adds its round trip to every
window; several readers at once; PostgreSQL on its own machine.

```sh
DATABASE_URL=postgres://$USER@localhost:5432/opengrid_dev \
  cargo run --release -p opengrid-server --example server_bench -- postgres 1000000
cargo run --release -p opengrid-server --example server_bench -- sqlite 10000000
COUNT_CACHE=1 cargo run --release -p opengrid-server --example server_bench -- sqlite 10000000
```

The first run writes the rows (`bench_orders_<rows>` in the database,
`target/bench-orders-<rows>.sqlite`) and keeps them for the next; the peak memory is read with
`/usr/bin/time -l`.

## In the browser, as a visitor sees it

The measuring tool in `bench/` opens a built page in a fresh Chromium, hands it the same
deterministic rows and times what a reader waits for, to **the frame that shows the right
answer** (the check reads the DOM, then waits one frame more, so 33 ms is two frames at 60 Hz and
the floor of every figure here). Memory is the whole browser process tree, resident, minus an
empty page's — the Worker and WebAssembly count like everything else. Same machine as above
(**Apple M4 Pro**, Chromium 153), 17 November 2026, **median of five**, the CPU not throttled.

| 1,000,000 rows | released 0.17.0 | this checkout |
|---|---|---|
| First rows, rows handed over as JS objects | 2.35 s | **0.30 s** |
| First rows, CSV bytes handed over | 0.87 s | 0.59 s |
| Sort, filter, group by country with a sum | 35, 50, 100 ms | 32, 50, 83 ms |
| Page memory after loading, objects / CSV | 1,090 / 687 MiB | **378** / 636 MiB |
| 100,000 rows: first rows, objects / CSV | 215 / 153 ms | 112 / 128 ms |

The objects row is the one that moved: since #445 the rows cross into the Worker as typed
columns, not as JSON text. The page's own million objects are in the memory figure of that row
(the tool holds them to hand them over); with CSV the page holds the file's bytes instead.
Scrolling is a frame whatever the size: 120 steps of three rows and 20 jumps of 2,000 rows, p95
16.7 ms, no frame over 33 ms. The page fetches **546 KiB** brotli-compressed (21 KiB more than 0.17.0), 526 KiB of it
WebAssembly (engine and all elements); that is what a small table pays for and does not need.

With the rows in a database behind `opengrid-server` (SQLite on the same machine; the count
cache on, as it is by default; the network is the loopback) the page holds none of them:

| Scrolling a table in server mode | 100,000 rows | 1,000,000 rows |
|---|---|---|
| First rows | 53 ms | 56 ms |
| A step of three rows (p50) | 17 ms | 17 ms |
| A jump of 2,000 rows (p50) | 33 ms | 33 ms |
| A drag to the middle | 33 ms | 50 ms |
| Group by country with a sum | 50 ms | 283 ms |
| Requests, and bytes answered, for 141 moves | 139, 294 KiB | 140, 297 KiB |
| Page memory after loading | 72 MiB | 72 MiB |

Over ten million rows in PostgreSQL the jump is 83 ms and the drag to the middle 550 ms: the
database walks past five million rows (see the section above). `bench/baselines/` keeps these
figures, in the tool's own format, so that a later change can be compared with them on the same
machine (`just bench-local --baseline bench/baselines/main-2026-11-17-1000000.json`). With the
page's main thread throttled to a quarter and a sixth of its speed, objects handed over reach the
first rows in 244 ms and 333 ms at 100,000 rows, and in 644 ms and 928 ms at 1,000,000; those runs
are kept as `-x4-` and `-x6-` files. They are **not** a mid-range laptop: Chromium's throttle does
not reach a Worker, so the engine ran at the full speed of the M4 Pro and only the page's own work
was slowed. A figure for a slower machine needs a limit the kernel enforces on every thread: the
bench job's CPU quota (`bench/README.md`) is that.

## Against other grids

The same tool measured five other grids that are MIT-licensed, as each one's own
documentation sets up a plain grid: **AG Grid Community 36.3**, **RevoGrid 4.31**, **SlickGrid
6.0**, **Tabulator 6.7** and **w2ui 2.0**. Same rows, same six columns, same questions, the same
page and the same Chromium (**Apple M4 Pro**, 17 November 2026, **median of five**, the CPU not
throttled); every time is to the frame that shows the right answer, so 33 ms is two frames and
the floor. *Undo* is clearing the filter and the sort. Memory is the whole browser process tree
after loading; opengrid's first row is the rows handed over as JS objects, as every other grid is
given them (the CSV row is the engine's own input).

| 1,000,000 rows | First rows | Sort | Filter | Undo | Memory | Fetched (br) |
|---|---|---|---|---|---|---|
| **opengrid**, objects | 195 ms | **34 ms** | 50 ms | **50 ms** | 376 MiB | 546 KiB |
| **opengrid**, CSV | 600 ms | 38 ms | 50 ms | 50 ms | 641 MiB | 546 KiB |
| AG Grid Community | 555 ms | 736 ms | 312 ms | 833 ms | 524 MiB | 256 KiB |
| RevoGrid | 130 ms | 266 ms | 97 ms | 166 ms | 239 MiB | 93 KiB |
| SlickGrid | 75 ms | 211 ms | 47 ms | 466 ms | 257 MiB | 55 KiB |
| Tabulator | 191 ms | 1,424 ms | 278 ms | 1,434 ms | 441 MiB | 88 KiB |
| w2ui | 1,124 ms | 591 ms | 150 ms | 983 ms | 480 MiB | 157 KiB |

| 100,000 rows | First rows | Sort | Filter | Undo | Memory |
|---|---|---|---|---|---|
| **opengrid**, objects | 97 ms | 32 ms | 33 ms | 33 ms | 123 MiB |
| **opengrid**, CSV | 116 ms | 33 ms | 33 ms | 33 ms | 167 MiB |
| AG Grid Community | 95 ms | 57 ms | 50 ms | 67 ms | 139 MiB |
| RevoGrid | 115 ms | 96 ms | 83 ms | 83 ms | 65 MiB |
| SlickGrid | 17 ms | 20 ms | 33 ms | 50 ms | 58 MiB |
| Tabulator | 44 ms | 106 ms | 32 ms | 100 ms | 115 MiB |
| w2ui | 135 ms | 49 ms | 31 ms | 100 ms | 171 MiB |

**What the table says.** Over a million rows opengrid answers a sort in 34 ms where the others
need 211 ms to 1.4 s, and undoes a filter and a sort in 50 ms where they need 166 ms to 1.4 s;
only SlickGrid filters as fast (47 ms against 50 ms). Over a hundred thousand rows the grids are
within a few frames of each other, and SlickGrid is ahead. Scrolling is a frame in every one of
them (p95 16.7 ms): that is not where they differ.

**Why opengrid is faster where it is.**

- **The query runs on typed columns, not on objects.** A sort or a filter is a scan over a
  typed column in an engine written in Rust, not a comparison function called on a million
  JS objects. The engine's own figure for the same sort is 26 ms (above).
- **Only the visible rows cross.** The page asks for a window of rows and gets it as one binary
  answer, not every row, and scrolling is a frame at a million rows as it is at a hundred thousand.
- **The work is off the main thread.** The engine runs in a Worker, so a query does not block
  scrolling or typing.
- **Cost grows with the data and no faster.** Ten times the rows cost about ten times the time
  (see the first table of this page).
- **The cost is paid once, at loading.** Since #445 the rows are made into typed columns
  while the worker starts, so the table is ready for the first question. That is the one
  step a JavaScript grid does not have, and the first column of the tables shows what it costs.
- **The same engine can be on the server.** With the rows in a database behind
  `opengrid-server` the page holds none of them: 72 MiB at a million rows, a window every
  step (see above).

**Where opengrid is behind.** The page fetches 546 KiB, 526 KiB of it the WebAssembly engine,
against 55 to 256 KiB for the others; over a hundred thousand rows its first rows take 97 ms
where SlickGrid and Tabulator need 17 and 44 ms; over a million rows RevoGrid (130 ms) and
SlickGrid (75 ms) show their first rows sooner than opengrid's 195 ms; and handed objects, the
page holds both its objects and the engine's columns. A table that small does not need an engine.

**How far to trust it.** Each grid is set up by an adapter written from that grid's
documentation, by us, and not checked by its maintainers; a different setting can change a
figure, and we would rather be told. One machine, one browser, one question (sort, filter,
undo, scroll a large table): a grid that does more is not slower for it here, and a grid that
does less is not faster. The tool, the adapters and the method are in `bench/`; `pnpm bench`
repeats it. We also ran a commercial grid, DevExtreme DataGrid, to check our own figures
internally; its licence does not say whether results may be published, so this page has none of
it and claims nothing about it.

## What these figures are not

- **Not a browser measurement**, except where a section says so: the figures of the engine are
  its own; the page, the frame and the process memory are `bench/` (above) and
  `scripts/measure-grid.mjs` (`just measure-grid`), in Chromium and WebKit.
- **Not a comparison of everything.** The section "Against other grids" is one question, on
  five MIT-licensed grids; it says nothing about editing, accessibility, pivot or export, and
  nothing about a grid that is not in it.
- **One machine.** An M4 Pro is a fast laptop. A phone, or a laptop three years older, takes
  proportionally longer; run the script on the hardware your readers have.

## Repeat it

```sh
just wasm-build
node scripts/measure-queries.mjs --rows 100000,1000000 --runs 9

# Loading again, in Chromium (the engine and the elements as the package ships them)
just wasm-build packages/opengrid/engine && just wasm-build-components
node scripts/measure-reload.mjs --rows 1000000 --loads 10
```
