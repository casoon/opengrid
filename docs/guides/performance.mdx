The engine is Rust compiled to WebAssembly, so the question every page has to answer is what it
buys and what it costs. This page gives the figures for the engine **on its own**: no browser,
no rendering, no network — the module that answers a query, loaded in Node. They are measured,
dated, and repeatable with one script.

## What was measured

Measured on 14 November 2026 on an **Apple M4 Pro** (arm64), Node 24, with
`scripts/measure-queries.mjs`: one run thrown away, then nine, **median** shown with the
fastest and the slowest in brackets. Other programs were running on the machine, so a quiet one
will be a little faster. The rows are ten columns of the conformance data set's
shape — integers, text, an exact decimal, a float, a boolean, a date and a timestamp — as CSV.
The two load times are of 16 November 2026, after the CSV reader's third pass: about 170 MB of
CSV a second.

| 100,000 rows (CSV 7.4 MB) | Median | Range |
|---|---|---|
| Load the CSV | 59 ms | — |
| Filter: country and amount, first 100 rows | 1.6 ms | 1.6–3.8 ms |
| Text search in a column, first 100 rows | 4.1 ms | 4.0–4.6 ms |
| Sort by amount, top 100 | 3.0 ms | 2.9–3.4 ms |
| Group by country, sum and count | 9.6 ms | 9.5–10 ms |
| Group by customer (500 groups), sum | 10 ms | 10–11 ms |
| Pivot: country and customer, sum and count | 32 ms | 32–33 ms |
| **Module memory** after the load | **16.6 MiB** | |
| of which the columns | 6.9 MiB | |

| 1,000,000 rows (CSV 74.6 MB) | Median | Range |
|---|---|---|
| Load the CSV | 0.44 s | — |
| Filter: country and amount, first 100 rows | 15 ms | 15–16 ms |
| Text search in a column, first 100 rows | 40 ms | 39–40 ms |
| Sort by amount, top 100 | 26 ms | 25–26 ms |
| Group by country, sum and count | 99 ms | 99–101 ms |
| Group by customer (500 groups), sum | 105 ms | 105–106 ms |
| Pivot: country and customer, sum and count | 312 ms | 309–352 ms |
| **Module memory** after the load | **173 MiB** | |
| of which the columns | 69 MiB | |

Ten times the rows cost about ten times the time and about nine times the memory: the engine
scans typed columns, and nothing in these queries grows faster than the data.

## Two numbers for the engine's memory

The **columns** — the data itself, typed — take 6.9 MiB for 100,000 rows and 69 MiB for a
million: about seventy bytes a row for these ten columns and the three derived from them. An
integer takes as many bytes as its largest value needs — one for a count of 0–39, four for an id up
to a million, eight at most — and stays an integer; an exact decimal stays exact, a timestamp keeps
its microseconds, and a missing value costs a bit in a bitmap rather than a boxed object.

The **module memory** is larger, 16.6 and 173 MiB, because it also holds the room that reading
the CSV needed — the file's copy in the module, 71 MiB for the million rows — and WebAssembly
memory only grows. That is the number a page pays, and the one the engine's budget guards:
`peakmark.toml` fails a release whose scenario (100,000 rows loaded, queried and pivoted) needs
more than 26 MiB, or leaks from one run to the next. The queries add nothing to it: ten rounds of
all of them leave it where the load put it.

A file loaded **piece by piece** (`loadStream`, 4 MiB at a time) does not need the copy: the same
million rows leave the module at 112 MiB after the load and after the queries, which take their
temporaries from the same room.

The numbers are the same in the tab and on a server, because it is the same code.

## What the whole page holds

The engine's own memory is not what the browser shows. Measured in Chromium, the engine in a
Worker: the resident memory of the browser's whole process tree, minus an empty page's, after
a CSV file of the same shape (six columns) has been fetched and loaded. The page keeps no rows of
its own: a page that holds a million JavaScript objects pays for them on top.

| Rows | File | `load` of the bytes | `loadStream` of the response |
|---|---|---|---|
| 100,000 | 4.1 MB | 50–53 MiB | 45–46 MiB |
| 1,000,000 | 43 MB | 172–175 MiB | 142–145 MiB |

So the engine is **compact, not free**: it keeps its own typed copy of the data — about 160 MiB
for a million rows, 140 when the file is read in pieces (these two figures and the table are from
before the integers took only the bytes they need, which took 26 MiB off the module of a million
rows) — next to whatever the page holds.

A page that has its rows as JavaScript objects hands them over with `loadRows`, which turns them
into typed columns in pieces of 65,536 rows and does not make a JSON text of the table. Measured
the same way, on a page that generates its million objects itself (so the objects are in the
figure): 386 MiB, 1,000,000 rows, and the first rows on screen after 0.27 s. Before, as one JSON
text, it was 847 MiB and 1.2 s; for 100,000 rows 128 MiB and 0.1 s against 158 MiB and 0.17 s.

**Using the grid adds to that once, not each time.** After the first scroll through the table the
same process tree holds about 55 MiB more, for 100,000 rows and for a million alike: it is what
Chromium keeps for painting, in its renderer and GPU processes. The engine's memory, the page's
JavaScript heap and the number of elements in the grid stay where the load left them. Sorting and
filtering add nothing measurable, and ten more rounds of sort, filter and scroll add about 15 MiB
before it levels off.

## Loading again

WebAssembly memory grows and is never handed back to the browser. Inside the module, the
allocator reuses what a table frees, so a page that loads again stays at its **high-water mark**
instead of growing with each load. That high-water mark is set by how a page loads.

Measured on 16 November 2026 in Chromium on the same M4 Pro with `scripts/measure-reload.mjs`.
The engine runs in a worker, and each load is a million rows of the shape above. The table shows
the engine's memory (`stats().memory`) and the physical footprint of the browser's whole process
tree, minus the page with its CSV already fetched. Each row is a single run.

| Ten loads of 1,000,000 rows | Engine, after load 1 → 10 | Browser, after load 10 |
|---|---|---|
| Same name, `load` of the bytes | 173 → 251 MiB, flat from load 2 | 320 MiB |
| Same name, `loadStream` | 112 → 214 MiB, flat from load 3 | 210–295 MiB |
| Ten names, `loadStream` | 112 → 844 MiB, +82 MiB a table | 826 MiB |
| Same name ten times, then `terminate()` | — | 5 MiB |

- **A name loaded again replaces its table, all or nothing.** The new table is built in full
  before the old one goes, so a load that fails keeps the old data. For that moment both tables
  are in memory, and the high-water mark is about two tables. Fragmentation adds nothing
  measurable: two tables of 112 MiB leave 214 MiB.
- **Another name keeps the old table.** A page that switches between data sets under new names
  adds them up. There is no call that frees one table.
- **`terminate()` hands everything back.** It stops the worker, and its memory goes with it. A
  new provider that loads and answers once took 0.54 s, against 0.51 s for the same load into a
  worker already running. A page that is done with a data set can start over that cheaply.

So a page that loads data again and again uses one name and `loadStream`. When it needs to come
back down to one table, it ends the worker and starts a new provider. The server mode keeps only
the window in the browser.

## What a page pays

The engine is a module the page loads before its first query. Compressed with Brotli:

| Module | Size | Loaded |
|---|---|---|
| The engine (`engine/`) | about 172 KiB | when the page starts the engine |
| All three elements (`pkg/`) | about 348 KiB | with the elements |
| The collation of a locale (`collation/`) | about 325 KiB | only by a sort that names a locale |
| The XLSX writer (`xlsx/`) | about 240 KiB | only by an export to a workbook |

Sizes are kept inside budgets in `peakmark.toml`, so a release that grows one fails the build
until the growth is explained. A table of fifty rows does not need an engine, and the page
that only reads it should not pay for one.

## In a worker

The engine runs in a Web Worker as it runs on the page, so a query does not block the main
thread. The [live demo](https://og-vanilla.casoon.dev/large-data) queries 100,000 rows that way.
The figures above are the engine's own time; what the page adds is the transfer of the answer and
the drawing of the rows on screen.

## In server mode

With a [REST provider](../where-queries-run/) the rows stay in the database. The grid asks for
the window it shows — 40 rows by default — and the database filters, sorts, groups and counts.
What a reader waits for is then the server and the database, not the engine in the tab.

Measured on 16 November 2026 on the same **Apple M4 Pro**: `opengrid-server`, release build,
with one source, answering `POST /query` over the loopback in the binary result form, as
`createRestProvider` asks. PostgreSQL 16 ran on the same machine; SQLite is compiled into the
server. The rows are those of the engine figures above, generated by the database. Indexes as a
page tuned for these requests would have them: the key `id`, and `(country, amount)` for the
filtered window. One run thrown away, then nine, **median** shown; other programs were running
on the machine.

| A window of 40 rows, or a grouping | PostgreSQL, 1M | PostgreSQL, 10M | SQLite, 1M | SQLite, 10M |
|---|---|---|---|---|
| First window, sorted by `id` | 13 ms | 181 ms | 1.7 ms | 18 ms |
| Window in the middle (`offset` half the rows) | 32 ms | 396 ms | 12 ms | 119 ms |
| Filter on country and amount, sorted by amount | 48 ms | 513 ms | 1.8 ms | 16 ms |
| Text search in a column, any case | 80 ms | 957 ms | 121 ms | 1.18 s |
| Group by country, sum and count | 65 ms | 905 ms | 104 ms | 1.03 s |
| Count of every row (`limit` 0) | 13 ms | 168 ms | 1.6 ms | 18 ms |
| **Server's peak memory** | 9.5 MiB | 9.4 MiB | 16 MiB | 17 MiB |

A window's answer is 3.3 KiB on the wire, a grouping's 352 bytes, whatever the table's size. The
server's memory is the whole process — server and the measuring client — and stays the same for
ten times the rows; PostgreSQL's own memory is not in it, SQLite's page cache is.

What the figures say:

- **Every window carries its count.** `total_count` is what the grid needs for its scroll bar and
  `aria-rowcount`, and it is a second statement for each window. In PostgreSQL counting ten million
  rows takes about 170 ms, and that is most of the first window's 181 ms.
- **A window far down costs more.** An `offset` makes the database walk past the rows before it:
  dragging the scroll bar to the middle of ten million rows asks for 400 ms in PostgreSQL.
- **The indexes decide, not opengrid.** With an index on `amount` alone, SQLite takes it for a
  range over half the table: the filtered window then needs **5.5 s** at ten million rows instead
  of 16 ms. A text search with `contains` reads every row in either database.
- **Compared with the tab.** A million rows in the engine answer a filter in 15 ms and a grouping
  in 99 ms, once the page has loaded them (0.44 s, 173 MiB in the engine). The server answers in
  the same order of magnitude, puts nothing but the window into the browser, and answers from the
  current data each time.

Not measured here: the network between browser and server, which adds its round trip to every
window; several readers at once; PostgreSQL on its own machine.

```sh
DATABASE_URL=postgres://$USER@localhost:5432/opengrid_dev \
  cargo run --release -p opengrid-server --example server_bench -- postgres 1000000
cargo run --release -p opengrid-server --example server_bench -- sqlite 10000000
```

The first run writes the rows (`bench_orders_<rows>` in the database,
`target/bench-orders-<rows>.sqlite`) and keeps them for the next; the peak memory is read with
`/usr/bin/time -l`.

## What these figures are not

- **Not a browser measurement.** Rendering, scrolling and the filter row are measured
  separately by `scripts/measure-grid.mjs` (`just measure-grid`), in Chromium and WebKit.
- **Not a comparison with other grids.** One would need the same data, the same features and
  each product set up as its own documentation recommends, and its method published before its
  result. That is planned, not done; until then this page says nothing about anyone else.
- **One machine.** An M4 Pro is a fast laptop. A phone, or a laptop three years older, takes
  proportionally longer; run the script on the hardware your readers have.

## Repeat it

```sh
just wasm-build
node scripts/measure-queries.mjs --rows 100000,1000000 --runs 9

# Loading again, in Chromium (the engine and the elements as the package ships them)
just wasm-build packages/opengrid/engine && just wasm-build-components
node scripts/measure-reload.mjs --rows 1000000 --loads 10
```
